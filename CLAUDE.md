# NYC comedy list

`build.py` fetches lineups from NYC comedy venues and writes `index.html`: a table of comedians, each with two ratings and their shows. `rate.py` makes the ratings with the claude CLI, against a taste written in `taste.txt`.

## Run

```
python3 build.py                 # fetch, write data/shows.json and index.html (about 20 requests, 30 seconds)
python3 build.py --nights 14     # default is 7 nights, from tonight
python3 build.py --render-only   # rebuild index.html from data/shows.json, no network
python3 rate.py                  # rate the comedians that ratings.json lacks (needs the claude CLI)
python3 rate.py --all            # rate everyone again
python3 rate.py --backend ollama # rate with a local Gemma through Ollama instead of the claude CLI
python3 build.py --render-only   # put the new ratings on the page
python3 -m unittest discover tests
```

For a new taste: edit `taste.txt`, run `rate.py` (a changed taste rates everyone again), then `build.py --render-only`.
`rate.py --taste X --ratings Y` and `build.py --ratings Y --taste X --out Z` work on other files, for the examples or a second taste side by side.

Needs `requests` and `beautifulsoup4`. `uv run build.py` installs them from the script header.
`rate.py` needs the `claude` CLI on the PATH and logged in. It calls `claude -p --tools ""` once per batch of 30 names, 6 batches at once. A full run of 270 names takes about 30 seconds with the default `sonnet` model, 70 seconds with `--model opus`. `haiku` is not faster in practice and knows few comedians (19 rated against 54 for sonnet and 70 for opus). A failed call is retried once, then its batch is skipped; the next run picks those names up. Answers vary a little from run to run.
For the Ollama backend: Ollama is installed without sudo in `~/.local/opt/ollama/bin/ollama`. Start the server with `~/.local/opt/ollama/bin/ollama serve` (in another terminal or in the background), pull a model once with `ollama pull gemma4:12b`, then run `rate.py --backend ollama`. The machine has an 8 GB GPU, so the 12B model runs partly on the GPU and partly in RAM. Batches are 10 names, one call at a time.

`tests/test_filters.py` runs the page script in headless Chromium. Without Chromium, it is skipped.

## Files

- `build.py`: fetch and render. One `parse_*` and one `fetch_*` function per venue, then the HTML render.
- `rate.py`: builds the prompt, calls the claude CLI, parses the answer, writes `ratings.json`.
- `taste.txt`: the taste, in plain words. Anyone edits this.
- `ratings.json`: the ratings. Generated by `rate.py`. See "Ratings".
- `data/shows.json`: the last fetch. Generated. `--render-only` reads it.
- `index.html`: the page. Generated. Do not edit by hand.
- `tests/test_build.py`: parser, ratings and render tests. They use `tests/fixtures/`, small cuts of real responses.
- `tests/test_rate.py`: prompt and answer parsing of `rate.py`. No test calls the CLI.
- `tests/test_filters.py`: browser test of the filters, on a small fixed page.
- `README.md`: how to use the project, for people who do not change the code. Keep it short.
- `examples/<name>/`: a finished page per taste: `taste.txt`, `ratings.json`, `index.html`. Rebuild one with
  `python3 rate.py --all --taste examples/<name>/taste.txt --ratings examples/<name>/ratings.json` then
  `python3 build.py --render-only --ratings examples/<name>/ratings.json --taste examples/<name>/taste.txt --out examples/<name>/index.html`.
  They share `data/shows.json`, so they show the week of the last download.
- `.scratch_pads/` (not in git): saved full responses, `make_fixtures.py`, `wikipedia_check.py`, `filter_check.py` (filters against live data), screenshots.

## The page

One row per comedian. Columns: Comedian, Profile, Taste fit, Shows.
Filters: name, night, location, profile, taste fit. A filter on night or location also hides the shows that do not match.
Rows are in name order.

## Venues

| Venue | Source | Notes |
|---|---|---|
| Comedy Cellar | `POST https://www.comedycellar.com/lineup/api/`, one call per night | Lineups reach about 6 nights ahead. |
| The Stand | `https://thestandnyc.com/shows`, 20 shows per page, follow "More Shows" | Date and time come from the show URL. |
| New York Comedy Club | `https://newyorkcomedyclub.com/calendar/YYYY-MM`, schema.org `ComedyEvent` JSON | Lineups reach about 5 nights ahead. robots.txt asks for a 3-second delay. |

Gotham Comedy Club is not included. Its site publishes show titles only, no comedian names.

To add a venue: write `parse_x` and `fetch_x`, set `location` on each show, add one line to `VENUES`, add a fixture and tests.

## Locations

A show has a `venue`, a `room` and a `location`. The location is the address to go to. The location filter uses it.

- Comedy Cellar: one location. Its rooms are in two buildings on the same corner.
- The Stand (116 E 16th St) and The Stand West (407 W 15th St) are two locations. The site lists The Stand West as a room.
- New York Comedy Club: three locations: Midtown, Upper West Side, East Village.

## Ratings

`rate.py` asks the claude CLI to rate each comedian on two scales and writes `ratings.json`: name -> at most two ratings, each a tier and a short reason (`profile` + `profile_why`, `taste` + `taste_why`).

- `profile`: `star` (big name), `known`, `rising` (rising star).
- `taste`: `strong`, `partial`, `different`: fit with the taste in `taste.txt`. "different" is about style, not quality.

The prompt (`PROMPT` in `rate.py`) tells the model to rate a scale only when it is confident it knows the comedian, else `null`, and to keep reasons to facts it is sure of. An empty entry `{}` in `ratings.json` means the model did not know the name; the page shows "Not rated". The answers are judgments from the model's general knowledge and are not verified. `ratings.json` records the taste text and the model, and the page footer names them.

`rate.py` skips names that `ratings.json` already has. A changed `taste.txt` makes it rate everyone again. `build.py` works without `ratings.json` (everyone "Not rated") and stops if a tier is unknown or a reason is missing. The scales and their page labels are in `SCALES` in `build.py`; the prompt reads them from there, so the tier meanings must stay taste-neutral ("close to this taste", not "dark comedy").

`build.py` warns, in the terminal and in the page footer, when `taste.txt` changed after `ratings.json` was made.

## Rules that the code follows

- A show `start` is NYC local time on the real calendar day. The Cellar bills a 12:30 AM show under the night before; `parse_cellar` moves it to the next day.
- A night ends at 04:00 (`NIGHT_ENDS_HOUR`). `night_of()` decides which night a show belongs to. The window and the night filter count in nights.
- A show with no published lineup stays in `data/shows.json` but not on the page. The page footer counts these shows.
- A venue whose site fails (HTTP error, bot challenge, no lineups at all) is skipped. `data/shows.json` lists it under `failed` and the page footer names it. The build stops only when every venue fails. The Stand has been behind a Cloudflare challenge since Oct 2026.
- Comedy Cellar shows link to the lineup page. The reservation links in the API carry today's date for every night, so they are wrong for later nights.
- `name_key()` merges spellings of one name (case, accents, apostrophes, periods). Ratings use the same key.
- `ALIASES` and `NOT_COMEDIANS` in `build.py` are hand-kept. Add a line when the page shows one person twice, or shows a show name as a person.
- All scraped text is HTML-escaped. Only `https://` links become links.
- The page CSS sets `display` on rows and list items, so it needs the `[hidden] { display: none !important }` rule for the filters to hide them.
